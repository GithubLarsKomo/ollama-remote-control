# ADR-0004 — Local admin password and session security

- **State:** accepted
- **Date:** 2026-08-08
- **Accepted:** 2026-08-08
- **Decision owner/approver:** product owner

## Question

How should the MVP store the local administrator password and represent browser sessions without persisting reusable plaintext authentication material?

## Constraints

- The approved SPEC requires a local administrator and modern password hashing, preferably Argon2id.
- Passwords must never be reversibly encrypted or stored in plaintext.
- Session cookies must be `Secure`, `HttpOnly` and `SameSite=Lax` or stricter.
- Authenticated mutations require CSRF protection.
- The application runs on Node.js 24 LTS.

## Evidence

- OWASP recommends Argon2id and lists `m=19456 KiB`, `t=2`, `p=1` as a minimum-equivalent profile.
- Node.js 24 includes `crypto.argon2()` from v24.7.0, but the Node 24 documentation still marks the API as release-candidate stability.
- `argon2` 0.45.1 binds the reference Argon2 implementation, supports Argon2id, is actively maintained and supports Node.js >=22.
- Session and CSRF tokens generated from 32 cryptographically random bytes have 256 bits of source entropy; unlike human passwords they do not require a slow password KDF before database storage.

## Alternatives

### A. Node 24 built-in `crypto.argon2`

**Benefit:** no extra dependency.  
**Rejected for this slice:** release-candidate API stability in the selected Node 24 LTS line.

### B. `argon2` package with Argon2id

**Benefit:** established password-hashing API, encoded salt/parameters in the resulting hash, actively maintained, compatible with Node 24.  
**Cost:** another native dependency and supply-chain/build surface.

### C. Node built-in `scrypt`

**Benefit:** stable platform API and no dependency.  
**Cost:** valid fallback, but contrary to the SPEC preference when a mature Argon2id implementation is available.

## Decision

Use **Alternative B** for local administrator passwords:

```text
Argon2id
memoryCost = 19456 KiB
timeCost = 2
parallelism = 1
unique random salt generated by the library
```

For sessions:

- generate session token: 32 random bytes, Base64URL encoded;
- persist only `SHA-256(session_token)`;
- send raw session token only as an `orc_session` cookie with `Secure; HttpOnly; SameSite=Strict; Path=/`;
- default server-side lifetime: 12 hours;
- revoked or expired sessions are invalid even if a browser still holds the cookie.

For CSRF:

- generate a separate 32-byte random token for each session;
- persist only `SHA-256(csrf_token)`;
- expose the raw CSRF token in a separate `Secure; SameSite=Strict` non-HttpOnly cookie so the same-origin SPA can copy it into `X-CSRF-Token`;
- authenticated mutations require both cookie/header equality and server-side digest verification.

Initial login brute-force protection is a per-process, per-client-IP failure window: five failed attempts per 60 seconds. A successful login resets the bucket. Distributed rate limiting is deferred until deployment topology requires more than one application replica.

## Security boundaries

- Password hashes are never returned to the browser.
- Raw session and CSRF tokens are never persisted.
- Login responses use the same public error for unknown username and wrong password.
- Unknown-user login performs an Argon2 operation to reduce username timing disclosure.
- Login username/password sizes are bounded before an expensive Argon2 verify operation.
- Admin bootstrap uses an atomic SQLite insert guard so concurrent bootstrap requests cannot create multiple initial administrators.

## Validation evidence

The final read-only GitHub Actions run used the committed lockfile with `npm ci` and passed:

1. Argon2id hashes stored instead of plaintext passwords — **passed**.
2. concurrent bootstrap creates exactly one administrator — **passed**.
3. valid login sets both cookies with required security attributes — **passed**.
4. only session and CSRF token digests are present in SQLite — **passed**.
5. current-session lookup rejects revoked and expired sessions — **passed**.
6. logout without matching CSRF header fails — **passed**.
7. valid logout revokes the server-side session — **passed**.
8. five failed logins trigger a 60-second per-IP rate limit and recover after expiry — **passed**.
9. oversized login input is rejected before expensive password verification — **passed**.
10. existing foundation, SSH, streaming and Docker gates remain green — **passed**.

## Rollback / exit path

Password hashes encode their algorithm and work parameters. A later password hasher can be introduced through verification-and-rehash on successful login. Session token hashing and cookie names are internal application contracts and can be versioned independently of persisted host/Ollama data.
